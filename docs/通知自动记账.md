# 通知自动记账

手机上微信付完款，工作台自动出现一笔账，不用手动输入金额。

## 一、链路

```
Android APK（NotificationListenerService）
  │  白名单过滤（手机端执行，非白名单不上传）
  │  本地持久队列 + WorkManager 重试（断网不丢）
  ▼
POST /api/notify/receive        （session 鉴权，复用现有登录）
  │
  ├─ 解析（两层：渠道模板 → 通用兜底）
  ├─ 去重（金额 + 60 秒窗 + 双方商户都为空）
  │
  ├─ high   → 直接写 txn（source='notify'），5 分钟内可撤销
  ├─ medium → 写 pending_txn，工作台点确认才入账
  └─ 解析失败 → 写 raw_notification，工作台提示「有 N 条未识别」
```

**PWA 本身读不到系统通知**，所以必须有一个原生 APK 作为旁路。
`docs/验收指南.md` 里那条「无原生 App → 无法用系统级通知」的限制，正是这个模块要绕过的。

## 二、为什么置信度规则和分享通道不同

这是本模块最容易做错的地方。

真实微信支付通知（截图实测）：

```
标题：微信支付
正文：已支付¥16.88
```

**通知里没有商户。** 背景是京东收银台，但通知只告诉你「付了多少钱」。

而 `share-parse.ts` 的规则是：

```js
const confidence = hasCurrencyMarker && merchant ? 'high' : 'medium';
```

如果通知沿用这条规则，**所有微信通知都会是 medium**，全部进待确认，
自动记账退化成「一个需要手动点的队列」——等于没做。

因此 `notify-parse.ts` 用的是：

| 通道 | high 条件 |
|---|---|
| 分享（share-parse） | 带货币符号 **且** 拿到商户 |
| 通知（notify-parse） | **渠道已知 + 金额 + 支出/收入动词**（商户允许为空） |

商户为空时，命中的原文片段会写进 `txn.note`（`自动记账：已支付¥16.88`），
账单列表据此还能认出「这笔花在哪」。

## 三、去重规则

匹配条件：**金额相同 + 60 秒内 + 双方商户都为空**
仲裁方式：按渠道优先级保留一条（微信 > 支付宝 > 银行 > 未知）

两个容易搞反的点：

1. **渠道不参与匹配，只参与仲裁。**
   要解决的正是「微信 + 银行」的跨渠道重复，若把 channel 当匹配条件，
   两者永远匹配不上，去重直接失效。

2. **商户非空就不去重。**
   两杯 15 元咖啡间隔 30 秒是真实存在的；一旦任一方带了商户名，
   说明信息足够区分，两笔都记。

`txn` 表没有 `channel` 列，去重时 `source='notify'` 的记录统一按 `bank`（低优先级）处理 ——
宁可让新来的微信通知替换它，而不是反过来。

## 四、时间基准

用户拍板「以服务端接收时间为准」，但这和「断网恢复后不丢」冲突：
10 月 31 日晚付的款，11 月 1 日补传会落进 11 月，跨月汇总直接错。

实际实现：

```
默认用服务端接收时间；
APK 同时上报 postTime，两者偏差 > 5 分钟则回退到 postTime。
```

网络正常时两者几乎相等，不增加复杂度；断网补传时能落回付款当天。

## 五、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/notify/receive` | APK 上报一条通知 |
| GET | `/api/notify/config` | APK 拉白名单与去重窗 |
| PUT | `/api/notify/config` | 设置页改白名单/渠道映射/阈值 |
| GET | `/api/notify/pending` | 待确认列表 |
| POST | `/api/notify/pending/:id/confirm` | 确认转正（可覆盖账户/分类/金额） |
| DELETE | `/api/notify/pending/:id` | 忽略 |
| GET | `/api/notify/raw` | 未识别原文列表 |
| POST | `/api/notify/raw/:id/ignore` | 标记忽略 |
| POST | `/api/notify/heartbeat` | APK 心跳 |
| GET | `/api/notify/health` | 链路健康度（Dashboard 用） |

`/receive` 返回的 `action` 告诉 APK 该不该从本地队列删除：

| action | 含义 | APK 动作 |
|---|---|---|
| `recorded` | 已落库 | 可删 |
| `pending` | 进待确认 | 可删 |
| `raw` | 未识别，原文已存 | 可删 |
| `duplicate` | 重复 | 可删 |
| `rejected` | 白名单外/非法 | 可删，且不该重试 |

## 六、数据表

| 表 | 用途 |
|---|---|
| `pending_txn` | 低置信度待确认。独立成表而非给 `txn` 加 status —— 月度汇总不必到处加过滤，一个漏加就是算错账 |
| `raw_notification` | 解析失败的原文，与账本完全隔离 |
| `device_heartbeat` | 心跳。超 48 小时无心跳 → Dashboard 告警 |
| `app_config` | `notify.*` 前缀：渠道→账户映射、白名单、去重窗、默认分类 |

## 七、健康度告警

自动记账最隐蔽的故障是「某天微信改了文案 / APK 被系统杀掉，之后再也收不到通知，而你以为一切正常」。

`GET /api/notify/health` 返回：

```json
{
  "healthy": false,
  "warning": "已 52 小时无心跳（阈值 48 小时），通知采集可能已断开",
  "heartbeat_age_hours": 52,
  "pending_count": 3,
  "raw_new_count": 2
}
```

## 八、Android APK（`apps/android/`）

### 8.1 为什么不用 Gradle

仓库路径含空格（`Workstatin Me`）、本机 Java 是 1.8、Gradle 未安装、
Android SDK 的 `platforms/` 目录为空——Gradle + AGP 要下载数百 MB 依赖，
在这个环境里不确定性太大。

改成**手工构建链路**，每步可控、产物可验证：

```
aapt2 compile → aapt2 link → javac → d8 → zipalign → apksigner
```

APK 刻意**零第三方依赖**（不引 AndroidX / Material / WorkManager），
UI 用原生 `LinearLayout`，重试用 `AlarmManager`。产物只有 **25 KB**。

### 8.2 构建

```bash
# 前置：JDK 17 + Android SDK platform 28 + build-tools 29.0.3
export ANDROID_SDK_ROOT=/path/to/android-sdk
export JAVA_HOME=/path/to/jdk-17
bash apps/android/build.sh
# 产物：apps/android/dist/workstation-notify.apk
```

脚本自动适配 Windows（`.exe`/`.bat`）与 Linux/macOS（无后缀）。
CI 里同样调用这个脚本（`.github/workflows/ci.yml` 的 `android` job）。

### 8.3 组件

| 类 | 职责 |
|---|---|
| `NotifyListenerService` | 系统通知监听；白名单外的包直接 return，不上传 |
| `Queue` | 本地持久队列（SQLiteOpenHelper），断网/重启不丢 |
| `Api` | HTTP + session 登录 + 401 自动重登 |
| `Uploader` | 刷队列、指数退避重试、心跳 |
| `RetryReceiver` | AlarmManager 到点重试 |
| `SetupActivity` | 配置页：授权、服务器、账号、状态、调试注入 |
| `DebugReceiver` | adb 广播注入假通知（仅 debug 包生效） |

### 8.4 权限与隐私

只申请三个权限：

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
```

**不申请 `READ_SMS`** —— 短信走现有 share_target 通道。
通知使用权（`BIND_NOTIFICATION_LISTENER_SERVICE`）必须用户手动在系统设置里授予，
无法通过运行时权限弹窗获取，`SetupActivity` 负责跳转引导。

在 Android 9（API 28）模拟器上实测通过：

### 8.6 验证过程中踩到的坑（已修）

| 坑 | 现象 | 解法 |
|---|---|---|
| `ON CONFLICT` 不认部分唯一索引 | 待确认/未识别表插入报 SQL 错 | 改成普通 `UNIQUE INDEX`（NULL 互不冲突） |
| `txn` 缺幂等键 | 同一条通知重发被误判为「替换旧记录」 | 新增 `txn.dedupe_key` 列 + 唯一索引 |
| Android 8+ 后台广播限制 | `Background execution not allowed` | 广播必须带 `-n 包名/.DebugReceiver` 显式组件 |
| Windows 传中文乱码 | 服务端收到 `΢��֧��`，解析必然失败 | `DebugReceiver` 支持 `title_b64`/`body_b64` |
| `apply()` 异步写盘 | 心跳读到旧的 `sentTotal`，显示「已上报 0 条」 | 改用 `commit()` 同步写 |
| 模拟器连不上宿主机 | `10.0.2.2` 超时 | 用 `adb reverse tcp:8787 tcp:8787` |

## 九、前端（Dashboard + 收件箱）

### 9.1 四个入口

| 位置 | 内容 | 什么时候出现 |
|---|---|---|
| 首页横幅 | 「有 N 笔待确认 / M 条未识别」 | 有待处理项时 |
| 首页横幅 | 「⚠️ 通知采集可能已断开」 | 心跳超时或从未配置 |
| 首页 toast | 「自动记了一笔 -¥16.88」，5 分钟可撤销 | 最近 5 分钟有自动记账 |
| 收件箱页 `/notify` | 待确认列表 + 未识别原文 | 常驻 |

**为什么待确认单独一页而不是塞进首页卡片**：
处理时要看金额、商户、渠道、选账户，一张小卡片放不下。
首页只负责「告诉你几个」，决策在别的页做。

### 9.2 5 分钟撤销

高置信度通知直接落库，用户没有任何确认动作 —— 所以必须有一个反悔窗口。

撤销走 `POST /api/notify/undo/:id`，**不是**通用的 `DELETE /txns/:id`：

| 接口 | 能删什么 |
|---|---|
| `DELETE /txns/:id` | 任何记录、任何时间 |
| `POST /notify/undo/:id` | 只有 `source='notify'` **且** 5 分钟内 |

超窗口返回 `409 UNDO_EXPIRED`，手动记录返回 `409 NOT_AUTO`。
这两个限制都有测试覆盖。

### 9.3 「自动」标记

账单列表里 `source='notify'` 的记录带蓝色「自动」角标，
让你一眼看出哪笔不是自己敲的 —— 误记时更容易被发现。

### 9.4 未识别通知 → 手动记账

`/notify` 页点「手动记一笔」跳到 `/txn?raw=<id>`，
Txn 页会把那条通知的原文预填进备注，你对着原文填金额即可。
比让你重新回忆「刚才花了多少」好得多。

### 9.5 前端验证的局限（诚实说明）

本环境 `vite build` 因 esbuild 子进程被禁而失败，装不了 jsdom，
所以**无法做真实浏览器渲染验证**。

采取的办法：把易错的逻辑（金额符号、千分位、倒计时、渠道映射）
抽成纯函数 `notify-format.ts`，用 15 项测试覆盖；
TSX 组件只负责排版。

**这意味着**：样式、布局、点击行为未经真实验证，需要你打开页面看一眼。

## 十、部署

### 10.1 顺序绝对不能反

```bash
bash scripts/deploy.sh
```

脚本固化的顺序：

```
前置检查 → 类型检查 + 三套测试 → D1 迁移 → 前端构建 → wrangler deploy
```

**先迁移再 deploy**：如果反过来，新代码会打到还不存在的表上，
`/api/notify/*` 和 `/api/dashboard` 全部 500。

反过来（先迁移后部署）是安全的：旧代码不认识新表，但也不受影响。

### 10.2 前置条件

```bash
npx wrangler login
# 或者：export CLOUDFLARE_API_TOKEN=xxx
```

本机当前**没有登录态**（`~/.wrangler` 不存在），所以这一步必须你做。

### 10.3 迁移在生产库上安全吗

`0002_notify.sql` 对已有数据做过验证（用真实 SQLite 模拟）：

| 检查项 | 结果 |
|---|---|
| 在已有 3 笔历史账单的库上执行 | ✅ 成功 |
| 历史账单的 `dedupe_key` | ✅ 填 NULL，原数据不动 |
| 多个 NULL 的 `dedupe_key` | ✅ 不违反唯一索引 |
| 重复的非 NULL `dedupe_key` | ✅ 被拒绝（幂等生效） |

### 10.4 部署后自检

1. 打开线上地址，进「通知收件箱」
2. 首页看是否出现横幅
3. 手机 APK 的服务器地址改成**公网域名**（不能是 `127.0.0.1`）
4. 点「立即上传队列 + 心跳」，回工作台看健康度是否变成「正常」

> `workers.dev` 在国内被 DNS 污染（见 [部署记录](部署记录.md) 第四节），
> APK 建议直接指向自定义域名。
