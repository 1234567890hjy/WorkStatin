# 个人工作台 · 方案 v2（定稿）

- 日期：2026-10-22
- 状态：**可开发**（经 17 轮质询重构，v1 原方案不可直接实施）
- 定位：单人自用、数据归拢，不是产品
- 结论一句话：**方向成立，但 v1 的技术栈和模块清单要砍掉一大半；砍完才敢写第一行代码。**

---

## 一、评估结论：v1 哪里不成立

v1 提出 11 个模块、FastAPI + PostgreSQL 16 + Redis/BullMQ + Docker Compose、2C4G 云主机或 NAS、6 周交付。
逐条质询后，发现四个结构性错配：

| # | 错配 | 质询戳破的点 |
|---|------|-------------|
| 1 | **部署形态与核心场景矛盾** | 手机「分享导入」要求服务 **7×24 公网 HTTPS 可达**；而 NAS 只在局域网/回家才在线。两个前提互斥。 |
| 2 | **队列是凭空造出来的复杂度** | v1 假设 LLM 摘要是"慢任务"才需要 BullMQ。但它是**同步 HTTP 调用**，Workers 的 CPU 计时不含等待网络的时间，等 10 秒不烧 CPU → 队列、Redis、定时器整套消失。 |
| 3 | **视频 AI 学习是三个烂零件拼的** | `yt-dlp + ffmpeg + Whisper + GPU` 全塞进 2C4G，转写 1 小时视频要几十分钟，且这三个组件对 B 站/抖音的解析随时会失效。**转写外包给人**，系统只做「草稿 → 手动触发摘要 → 归档检索」。 |
| 4 | **字段级加密是安全表演** | AES-256-GCM 逐字段加密，防的只是"D1 被拖库"这一种场景，代价却是**聚合查询全废**（金额无法 SUM/ORDER BY）+ 密钥分发两难。真正的静态暴露面只有备份文件，**加密备份即可**。 |

### 保留的安全项（有真实威胁模型支撑）

- 口令哈希：**PBKDF2-SHA256（WebCrypto，10 万轮）** —— 原方案写 argon2，但 Workers 无原生 argon2，PBKDF2 是标准库内的正确选择，强度足够单人场景
- TLS（Cloudflare 默认）
- **加密备份文件**（唯一真实的静态暴露面）
- 登录限流（防爆破）

## 二、v2 技术栈

| 层 | v1 | v2 | 为什么换 |
|---|---|---|---|
| 计算 | 2C4G 云主机 / NAS | **Cloudflare Workers** | 固定成本 2C4G ≈ ¥30~60/月 → **0 元**；且天然 7×24 公网 HTTPS |
| 框架 | FastAPI (Python) | **Hono (TypeScript)** | 全栈同语言，一套类型贯穿前后端；Workers 首选 |
| 数据库 | PostgreSQL 16 | **D1 (SQLite)** | 单人 <100MB/5 年，SQLite 绰绰有余；免运维 |
| 物化视图 | PG materialized view | **汇总表 + 写时更新** | D1 无物化视图，改成写入时维护 `monthly_summary` |
| 队列 | Redis + BullMQ | **删除** | 见上表第 2 条 |
| 对象存储 | — | **R2** | 备份与附件，出网免费 |
| 前端 | React+TS+Vite+Tailwind+Recharts | **不变** | 这部分 v1 就是对的 |
| LLM | — | **DeepSeek API** | 国内直连、便宜；prompt 先在网页版手验再自动化 |
| ASR | Whisper/GPU | **外包**（通义听悟等） | 见上表第 3 条 |
| 通知 | 通知中心 | **Android Web Push** | 单人场景不需要统一通知中心 |

## 三、模块清单：11 → 7 + 设置

被砍（或降级）的：

| 原模块 | 处置 | 理由 |
|---|---|---|
| 统计报表（独立页） | **并入 Dashboard** | 独立页面没内容，Dashboard 一个图表区就够 |
| 通知中心 | **降级为 Android Web Push** | 单人不需要中心化通知 |
| 财务与资产（独立模块） | **与消费记录合并成一本账** | 支出/收入/转账本来就是一个 ledger |
| 天气提醒 | **降级为 Dashboard 卡片** | 前端懒加载 + 30 分钟缓存，不做定时推送；「天气×运动相关性」留 P2 |
| 系统设置 | 保留（薄） | 净资产手填、备份、口令 |

保留的 7 个：

1. **Dashboard** —— 汇总卡 + 图表区 + 天气卡
2. **记账**（消费+收入+转账合一）
3. **运动记录**
4. **视频 AI 学习**
5. **计划与任务** ← 本轮恢复
6. **日常管理** ← 本轮恢复
7. **设置**（净资产、备份、口令）

### 核心调度原则（贯穿全局）

> **任何模块在「本人连续使用 7 天」之前，不进路线图。**

这条原则是对 v1「11 个模块 6 周全交付」最根本的否定：先证明会用，再证明要做。

## 五、唯一致命风险

> **记账输入摩擦 vs 鲨鱼记账的 3 秒录入。**

鲨鱼记账已经做到「3 秒记一笔」，这是它唯一真正的护城河。
如果本工作台记一笔需要 10 秒，**它会被弃用** —— 不是"以后慢慢优化"，是从第一天就死。

因此 P0 的验收标准不是"功能跑通"，而是：

> **本人真的在户外用它记了 3 天账；比鲨鱼记账慢就返工。**

share_target 是这条护城河的正面进攻手段：短信/通知里已有金额和商户，分享一次即预填，用户只需确认。

## 七、风险登记

| 风险 | 等级 | 处置 |
|---|---|---|
| **Cloudflare 免费版国内延迟** | 高 | **用户自测**（工具已无法联网验证）；若不可接受则回退到国内 VPS，但成本从 0 → ¥30/月 |
| **记账输入摩擦导致弃用** | 高 | P0 验收即为此设；share_target + 手填双通道 |
| iOS PWA share_target 行为差异 | 中 | 用户主力 Android，iOS 仅 PC 旁路；不承诺 iOS 分享 |
| 短信内容格式差异 | 中 | 用户已验证含金额+商户；解析失败一律落回手填 |
| CloudStudio 生命周期策略 | — | **已放弃**，不再考虑 |
| B 站/抖音接口变动 | 中 | 视频模块只取**元数据**，不做下载；接口变了只影响标题/时长，不影响核心 |
| 单人维护负担 | 中 | 模块准入原则（连续用 7 天）即是对此的防御 |
